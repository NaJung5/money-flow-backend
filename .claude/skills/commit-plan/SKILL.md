# 커밋 계획 제안

## 절차
1. `git status -sb`로 브랜치, 원격과의 차이, 변경 파일을 확인한다.
2. `git diff`로 변경 내용을 확인하고, untracked 파일은 직접 읽는다.
3. 변경을 **주제별로** 묶는다.
   - 한 커밋은 한 가지 이유로 바뀐 것만 담는다.
   - 각 커밋은 그 커밋까지만 있어도 컴파일되고 테스트가 통과해야 한다. 기대값이 바뀐 테스트는 그 원인이 된 코드와 같은 커밋에 넣는다.
   - 나누면 중간 커밋이 깨지는 경우에는 억지로 나누지 말고 하나로 묶자고 제안한다.
4. 커밋에 넣으면 안 되는 파일을 확인한다.
   - 로컬 설정, IDE 설정, 개인 정보나 비밀값이 들어 있을 수 있는 파일
   - 이번 작업과 관계없는 변경
5. 아래 출력 형식으로 답한다.

## 커밋 메시지 규칙
- 접두사: `feat` / `fix` / `refactor` / `test` / `chore` / `style` / `docs`
- 형식: `접두사: 한글 설명` (한 줄)
- 이슈 브랜치(`<접두사>/<이슈번호>-...`)에서 작업 중이면 끝에 이슈 번호를 붙인다: `feat: 거래 수정 서비스 구현 (#13)`
- `Co-Authored-By` 같은 trailer는 붙이지 않는다.

## 출력 형식
커밋마다:
```bash
git add <파일들>
git commit -m "<접두사>: <한글 설명>"
```
- 이 커밋에 들어가는 내용 요약 (1~3줄)
- 이렇게 나눈 이유가 명확하지 않으면 한 줄 설명

마지막에:
- 제외한 파일과 이유
- 이미 원격에 푸시된 상태인지 (`ahead`/`behind` 여부)

## Git 규칙
- 개인 feature 브랜치에서 원격과 차이가 있으면 fetch 후 rebase를 우선 제안한다. 공유 브랜치(main 등)는 rebase하지 않는다.
- 이미 푸시한 커밋을 고쳐야 하면 `--force` 대신 `--force-with-lease`를 제안한다.

## 하지 말 것
- `git add`, `git commit`, `git push`를 직접 실행하지 않는다. 사용자가 직접 커밋한다.
- 사용자가 그 자리에서 "니가 커밋해"라고 명시적으로 요청한 경우에만 실행한다.
