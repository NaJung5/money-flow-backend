# 테스트 케이스 목록 작성

대상: $ARGUMENTS (비어 있으면 커밋되지 않은 변경에서 바뀐 메서드)

## 절차
1. 대상 코드를 읽는다. Service라면 호출하는 Entity 메서드와 Repository 쿼리까지 따라가서 실제로 어떤 검증이 어떤 순서로 실행되는지 확인한다.
2. 이미 있는 테스트 파일(`src/test/...`)을 읽어서 어떤 케이스가 이미 검증되는지 확인한다.
3. 아래 관점으로 케이스를 뽑는다.
4. 아래 출력 형식으로 답한다.

## 케이스를 뽑는 관점
- **정상**: 기대한 상태 변경이 실제로 일어나는가 (저장 값, `deletedAt` 설정 등)
- **경계값**: 50자/51자, 금액 0/1/음수, 빈 문자열/공백/null
- **Soft Delete**: 삭제된 대상 조회·수정·삭제, 삭제된 부모, 삭제된 하위만 있는 부모 삭제
- **상태**: 비활성 카테고리, SYSTEM 카테고리
- **도메인 규칙**: 거래 타입과 카테고리 타입 불일치(생성과 수정 모두), 카테고리 계층 2단계 초과, 자기 자신을 부모로 지정
- **중복**: 같은 이름+타입(최상위), 같은 이름+타입+부모(하위), 삭제된 카테고리와 이름이 같은 경우, 자기 자신은 중복에서 제외되는지
- **존재하지 않음**: 없는 ID
- **검증 순서**: 여러 조건이 동시에 걸릴 때 어떤 ErrorCode가 먼저 나오는지가 중요한 경우

## 출력 형식
테스트 계층별로 나눈다.
- **Entity 단위 테스트**: 도메인 규칙과 상태 변경
- **Service 테스트** (`@SpringBootTest` + `@Transactional`): 조회 조건, 중복 검사, Repository와의 조합
- **Controller 테스트** (MockMvc): `@Valid` 검증, HTTP 상태 코드, 응답 JSON, 실패 시 `verifyNoInteractions(service)`

각 케이스는 한 줄로:
`[ ] 상황 → 기대 결과 (ErrorCode 또는 상태 변경)` 이미 있는 테스트면 `[x]`와 테스트 메서드 이름을 붙인다.

마지막에 **우선순위가 높은 빠진 케이스 3개**를 따로 짚는다.

## 하지 말 것
- 테스트 코드를 작성하거나 파일을 수정하지 않는다. 목록만 준다.
- 사용자가 "테스트 코드 써줘"라고 명시하면 그때 작성한다.
