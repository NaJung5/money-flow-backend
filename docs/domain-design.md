# Money Flow 도메인 분석 및 설계 초안

## 1. 설계 방향

이번 설계에서는 디렉토리 구조나 구현 코드를 먼저 결정하기보다, 도메인의 책임과 규칙을 먼저 정의하는 방향으로 진행한다.

기본 흐름은 다음과 같다.

* 요구사항 분석
* 핵심 객체 식별
* 객체별 정보, 행동, 규칙, 관계 정의
* Entity 및 VO 후보 도출
* DB/JPA 관계 설계
* Service / Controller / Repository 구현
* 테스트

객체지향적으로 설계할 때는 디자인 패턴을 억지로 적용하기보다 다음 질문을 기준으로 판단한다.

> 이 로직은 누구의 책임인가?

또한 객체의 행동은 단순히 CRUD 동작을 의미하는 것이 아니라, 해당 객체가 자신의 상태를 변경하거나 자신의 상태를 기준으로 판단하는 행위를 의미한다.

---

# 2. Transaction

## 2.1 정보

Transaction은 하나의 거래를 표현한다.

현재 필요한 정보 후보는 다음과 같다.

* 거래 구분

    * 수입
    * 지출
* 금액
* 거래일
* 카테고리
* 메모
* 사용자
* 등록일시
* 수정일시

추가적으로 사용처 정보를 둘 수 있다.

### 거래일과 등록일시의 구분

거래일과 시스템 등록일시는 서로 다른 개념으로 본다.

예:

* 거래일: 2026-09-01
* 시스템 등록일시: 2026-09-02 14:00

과거 거래를 나중에 입력하는 상황이 존재할 수 있으므로 둘을 분리한다.

---

## 2.2 행동

Transaction 객체가 자신의 상태를 변경하는 행동을 중심으로 정의한다.

현재 후보:

* 금액을 변경한다.
* 거래일을 변경한다.
* 카테고리를 변경한다.
* 메모를 변경한다.
* 거래 구분을 변경한다.

`거래를 등록한다`, `거래를 삭제한다`는 Transaction 객체 자체의 행동보다는 Repository 또는 애플리케이션 서비스의 책임으로 본다.

---

## 2.3 규칙

현재 정의된 규칙:

* 거래 금액은 정수만 허용한다.
* 0원 거래는 허용하지 않는다.
* 음수 금액은 허용하지 않는다.
* 비즈니스상 별도의 최대 금액 제한은 두지 않는다.
* 거래는 반드시 수입 또는 지출 중 하나의 거래 구분을 가진다.
* 거래일은 반드시 존재해야 한다.
* 카테고리는 상위 카테고리만 지정해도 거래 등록이 가능하다.
* Transaction의 거래 구분과 Category의 거래 구분은 반드시 일치해야 한다.
* 거래 구분을 변경하는 경우 변경된 거래 구분에 맞는 카테고리도 함께 지정해야 한다.
* 비활성화된 Category는 신규 Transaction에 사용할 수 없다.

금액 자체에는 항상 양수 값을 저장하고, 수입/지출의 의미는 거래 구분으로 표현하는 방향을 우선 검토한다.

---

## 2.4 관계

### Transaction - Category

거래 하나는 하나의 카테고리를 가진다.

같은 카테고리는 여러 거래에서 사용할 수 있다.

따라서 관계는 다음과 같다.

```text
Category 1 : N Transaction
Transaction N : 1 Category
```

상위 카테고리와 하위 카테고리 모두 Transaction에 직접 연결할 수 있는 방향을 우선 검토한다.

이 경우 상위 카테고리 통계는 다음을 모두 포함해야 한다.

* 상위 카테고리에 직접 연결된 거래
* 하위 카테고리에 연결된 거래

### Transaction - User

한 명의 사용자는 여러 Transaction을 가질 수 있다.

```text
User 1 : N Transaction
Transaction N : 1 User
```

비회원 거래를 지원한다면 Transaction의 User 관계는 선택적으로 둘 수 있다.

이 정책은 추후 회원 정책을 정의하면서 다시 결정한다.

---

# 3. Category

## 3.1 기본 방향

Category는 계층형 구조를 사용한다.

최대 깊이는 2단계로 제한한다.

예:

```text
식비
├─ 아침
├─ 점심
├─ 저녁
└─ 카페

교통
├─ 버스
├─ 지하철
└─ 택시
```

별도의 부모 Category 클래스와 자식 Category 클래스를 만들기보다 하나의 Category가 부모 또는 자식 역할을 할 수 있도록 설계하는 방향을 사용한다.

---

## 3.2 정보

현재 필요한 정보 후보:

* 카테고리명
* 거래 구분

    * 수입
    * 지출
* 활성화 여부
* 시스템 기본 / 사용자 커스텀 구분
* 부모 카테고리
* 사용자
* 등록일시
* 수정일시

`대분류`, `소분류`를 별도의 고정 필드로 두기보다는 Category 자신이 부모 Category를 참조하는 방식으로 계층을 표현하는 것을 우선 검토한다.

---

## 3.3 행동

Category 객체가 자신의 상태를 변경하는 행동 후보:

* 카테고리를 활성화한다.
* 카테고리를 비활성화한다.
* 카테고리 이름을 변경한다.
* 자식 카테고리를 추가한다.

다만 모든 행동이 모든 Category에 허용되는 것은 아니며, 시스템 기본 Category와 사용자 커스텀 Category의 규칙에 따라 제한한다.

---

## 3.4 규칙

### 공통 규칙

* 계층 깊이는 최대 2단계까지만 허용한다.
* 하위 Category는 또 다른 하위 Category를 가질 수 없다.
* 부모 Category와 자식 Category의 거래 구분은 반드시 동일해야 한다.
* Transaction의 거래 구분과 Category의 거래 구분은 반드시 동일해야 한다.
* 비활성화된 Category는 신규 거래에 사용할 수 없다.

### 시스템 기본 Category

* 시스템에서 기본 제공한다.
* 사용자가 임의로 수정할 수 없다.
* 사용자가 삭제할 수 없다.
* 시스템 기본 상위 Category 아래에 사용자가 커스텀 하위 Category를 추가하는 것은 허용한다.

### 사용자 커스텀 Category

* 사용자가 직접 생성할 수 있다.
* 사용자가 이름을 수정할 수 있다.
* 비활성화할 수 있다.
* 사용자만의 상위 Category 생성도 허용하는 방향을 우선 검토한다.
* 커스텀 상위 Category 아래에도 커스텀 하위 Category를 추가할 수 있다.

실제 DB 삭제보다는 비활성화 또는 Soft Delete 방식이 기존 거래 이력을 보존하기에 유리하다.

---

## 3.5 관계

### Category - Transaction

하나의 Category는 여러 Transaction에서 사용될 수 있다.

```text
Category 1 : N Transaction
```

### Category - Category

Category는 자기참조 관계를 가진다.

* 하나의 Category는 부모 Category를 0개 또는 1개 가진다.
* 하나의 Category는 자식 Category를 여러 개 가질 수 있다.
* 최대 깊이는 2단계로 제한한다.

개념적으로:

```text
Category
├─ parent: 0..1
└─ children: 0..N
```

### Category - User

사용자 커스텀 Category는 특정 사용자에게 속한다.

```text
User 1 : N Category
Category N : 1 User
```

시스템 기본 Category는 특정 User에 종속되지 않을 수 있다.

---

# 4. 현재까지의 주요 설계 결정

1. 가계부 Category는 계층형 구조를 사용한다.
2. Category 계층은 최대 2단계까지만 허용한다.
3. Transaction은 상위 Category만 지정해도 등록할 수 있는 방향을 우선 검토한다.
4. Transaction과 Category는 각각 수입/지출 거래 구분을 가진다.
5. Transaction과 Category의 거래 구분은 반드시 일치해야 한다.
6. 부모 Category와 자식 Category의 거래 구분도 반드시 동일해야 한다.
7. 시스템 기본 상위 Category 아래에 사용자가 커스텀 하위 Category를 추가할 수 있다.
8. 사용자만의 커스텀 상위 Category 생성도 허용하는 방향을 우선 검토한다.
9. 시스템 기본 Category는 사용자가 수정하거나 삭제할 수 없다.
10. 커스텀 Category는 수정 및 비활성화가 가능하다.
11. Transaction 금액은 0보다 큰 정수만 허용한다.
12. Transaction의 거래 구분이 변경되면 Category도 변경된 거래 구분에 맞아야 한다.

# 5. 아직 결정하지 않은 사항

추후 구현 전에 추가로 판단해야 할 내용이다.

## Transaction

* 사용처를 단순 문자열로 둘지 별도의 객체로 관리할지
* 비회원 Transaction을 실제로 지원할지
* 거래 구분 변경을 실제로 허용할지
* 거래 수정 가능 범위를 어디까지 둘지

## Category

* 같은 이름의 Category 중복 허용 기준

    * 사용자
    * 거래 구분
    * 부모 Category
    * 이름
* Category 삭제 정책

    * 완전 삭제
    * 비활성화
    * Soft Delete
* 시스템 기본 하위 Category도 제공할지
* 시스템 기본 하위 Category 수정/삭제 정책
* 상위 Category와 하위 Category 모두 Transaction에 직접 연결할지 최종 확정
* 커스텀 Category 최대 개수 제한 여부

## User

* 비회원 사용 지원 여부
* 회원 가입 시 기본 Category를 사용자별로 복제할지
* 시스템 공통 Category를 모든 사용자가 공유할지

1. Transaction / Category의 Entity 후보 확정

3. User 도메인 정의

5. DB 테이블 구조 및 제약조건 설계
6. Repository 책임 정의
7. Service의 오케스트레이션 책임 정의
8. Request / Response DTO 설계
9. API 설계
10. 테스트 시나리오 작성

구현 코드는 설계가 어느 정도 확정된 이후 작성한다.
